# Technical Debt Tracker

Open follow-up work. Remove a row when it is done.

| Item                                 | Area         | Notes                                                                                                                                                                                                                                      |
|--------------------------------------|--------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Runtime coverage                     | Validation   | The 26.4 runtime matrix and a run with the Vulkan validation layer passed on one GPU and driver; see the GPU Validation Matrix in `docs/RELIABILITY.md`. Before mesh terrain is called generally usable it needs other GPUs and drivers, and a check of the ordering inside its passes, which reach their buffers through the descriptor heap and device addresses and so are not taken as checked by synchronization validation. A GPU without the mod's features now keeps Minecraft's Vulkan renderer with the mod off (checked on an AMD integrated GPU, 2026-11-04); the mod's own paths have still run on one GPU only. |
| Mesh replacement as the default      | Renderer     | Replacement and strict cancellation are opt-in. Making them the default needs its own plan and the runtime coverage above.                                                                                                                 |
| Occlusion beyond GPU-driven terrain  | Renderer     | GPU-driven terrain is culled against a depth pyramid with improved transparency on (`vim.terrainOcclusionCulling`), and entities and block entities can be from results two or three frames late (`vim.entityOcclusionCulling`, off by default for that lag). The listed path is not; nor is anything without improved transparency, which the mod does not build for. Leaves let the sky's depth through their holes, so forest hides little. |
| Entity occlusion without lag         | Renderer     | Minecraft extracts entities on the CPU before the frame is drawn, so `vim.entityOcclusionCulling` can only use results a few frames old, and something stepping out from behind terrain shows that late. The model mesh stage could cull models against the frame's own pyramid instead, which would save GPU work but not the extraction. |
| Level of detail and eviction         | Renderer     | There is no level-of-detail page and no eviction by budget. Growing a terrain buffer re-uploads from copies kept on the CPU.                                                                                                                 |
| Visibility input from Minecraft      | Renderer     | On the multi-draw-indirect path Minecraft's indirect command buffer already holds one record per visible section layer and could replace the page list the mod uploads.                                                                    |
| RT/PT acceleration structures        | Renderer     | The data contracts and the capability gate exist. Allocation needs its own plan, starting from Before The First RT/PT Allocation in `docs/RELIABILITY.md`.                                                                                 |
| Accelerated worldgen provider        | Worldgen     | Provider detection is diagnostics only. Provider-owned world generation needs its own plan.                                                                                                                                                |
| Model mesh shaders as default        | Renderer     | `vim.gpuModelMeshShaders` draws identical frames, its run with the Vulkan validation layer is clean, and it takes less GPU time than the vertex pass, but the frame rate does not move, with the render thread setting the pace at 1920x1080 or the GPU at 3840x2160. It stays off until it buys something; a task stage would not (see Design Decisions in `ARCHITECTURE.md`). |
| GPU-driven frames in dense forest    | Performance  | At the ground at render distance 16, looking into spruce forest with culling off, GPU-driven frames run about 10 % slower than the listed path (1,241 to 1,269 against 1,411 to 1,433 FPS) where the GPU sets the pace. Terrain's own GPU time differs by the GPU-driven pass's 0.012 ms; the rest falls after terrain, 0.028 ms in the transparency passes and about 0.05 ms between frames, and only in leafy views (an ocean view and one down at the forest floor differ by the pass alone). Draw order within a distance step differs from Minecraft's, which may leave the depth costlier to read; a GPU trace would show it, and Nsight Systems needs its Vulkan layer registered in the system registry, which takes administrator rights. |
| Translucent terrain on the mesh path | Renderer     | Minecraft draws it with improved transparency in three order-independent stages, so the mesh path would need no sort, but a mesh pipeline and fragment work for each stage. Over an ocean at render distance 32 the GPU sets the pace (0.71 ms of render thread in a 2.2 ms frame), with walking the water's sections about a fifth of the render thread, so it would pay only where the CPU sets the pace. |
| Culled frames in leaf gaps           | Renderer     | Frames of a still scene culled by occlusion vary by one level in up to about 200 pixels in the gaps of dense leaves, where frames without culling vary in one; most likely coplanar faces of neighbouring sections swapping order as pages move between the phases. |
